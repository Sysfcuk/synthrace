# M0 performance and size measurements

These were measured on 2026-11-24 on the development machine: a Windows 11 laptop with an NVIDIA RTX 3060 Laptop GPU and an AMD Radeon integrated GPU, Rust 1.100.0, wgpu 30.0.2, trunk 0.22.2 and wasm-opt version_131.

## Download size

All figures are gzip -9 sizes. GitHub Pages serves gzip only, with no Brotli.

| Artifact | Raw | Gzip | Budget (gzip) |
|---|---|---|---|
| Game wasm (`opt-level=3`, wasm-opt `-O3`). wgpu with **both** `webgpu` and `webgl`, plus the renderer and embedded DSP. | 2,724,532 B | **1,023,015 B (0.98 MiB)** | ≤ 2.5 MB ✅ |
| Game wasm (`opt-level="s"`, wasm-opt `-O3`) | 2,302,876 B | 896,208 B | — |
| wasm-bindgen JS glue | 127,939 B | 19,725 B | — |
| `index.html` | 2,643 B | 1,372 B | — |
| DSP worklet wasm (embedded in the game wasm, so not a separate download) | 16,321 B | 6,915 B | ≤ 150 KB ✅ |
| **Total first load** | | **≈ 1.04 MB** | ≤ 3.5 MB ✅ |

**Decision:** keep `opt-level=3` for now. The 12% size saving from `"s"` is not worth a possible frame-time cost. Revisit in M6 using frame-time evidence from the reference phone.

## GPU / CPU frame time

These come from the native headless runner (`cargo run -p desktop --release -- --bench 300`). The renderer is held to `Limits::downlevel_webgl2_defaults()`.

Each sample is a full frame: CPU encode and submit, followed by a blocking GPU wait. That makes these numbers an upper bound on GPU time.

| Backend / GPU | Resolution | p50 | p95 | p99 | Draws | Passes |
|---|---|---|---|---|---|---|
| Vulkan, RTX 3060 Laptop | 1920×1080 | 1.32 ms | 1.38 ms | 1.39 ms | 14 | 13 |
| GLES (WGL), AMD Radeon iGPU | 1920×1080 | 7.30 ms | 8.00 ms | 8.25 ms | 14 | 13 |
| GLES (WGL), AMD Radeon iGPU | 1280×720 | 5.02 ms | 5.76 ms | 6.03 ms | 14 | 13 |

**In the browser** (Chromium-based built-in browser, AMD iGPU through ANGLE/D3D11, forced WebGL2, 1024×768 canvas), the debug overlay showed p50 **7.7 ms** (about 130 fps).

The browser pane was hidden during testing, so `requestAnimationFrame` was throttled at times. That makes the browser numbers indicative only: the p95 readings of about 1000 ms were caused by throttling, not by rendering. **WebGPU frame times in the browser were not measured for the same reason.** That check is still outstanding.

## Audio DSP cost

Measured in the browser as WebAssembly: the same `dsp_worklet.wasm`, instantiated with **zero imports**.

| Scenario | Result |
|---|---|
| 20 s of 48 kHz stereo audio, every layer on (3×7 PolyBLEP supersaw voices, bass + sub, arp, kick, hats, SVF filters, tanh bus) | Rendered in 210 ms, **≈ 1.05% of one core** |
